# 公网暴露风险调研（只给建议，未改代码）

对象：Gateway 的 HTTP 接口。结论先行——
**最关键的一道闸（注册必须凭邀请码）是有的，所以不会被任意人白嫖算力；
但缺少限流，登录/注册/提交三个口子都能被高频打，这是上公网前最该补的。**

---

## 一、已经守住的（不用改）

| 面 | 现状 |
|---|---|
| **注册** | **必须带 `invite_code`**，且校验过期/用尽/吊销。陌生人无法自助注册 ⇒ 不会被白嫖生成算力 |
| **所有业务接口** | 一律 `currentUser(req)` + 401。会话、任务、历史、素材全都要登录 |
| **管理接口** | 额外判 `role !== 'admin'`。`/api/admin/*` 普通用户拿不到 |
| **产物归属** | `serveAsset` 校验 `user_id`，只有本人（或管理员）能取；**不暴露 `storage_path`** |
| **产物时机** | 本版已补齐四个出口的终态门控，跑着的任务**猜到 URL 也拉不到**中间产物 |
| **内部接口** | `/internal/*` 用共享 token，与浏览器会话隔离 |
| **幂等** | 提交任务强制 `Idempotency-Key`，重放直接返回原 job，不会重复烧算力 |
| **单会话串行** | 同一会话有未完成任务时拒绝新提交（`SESSION_BUSY`） |
| **上传** | multipart 限 500MB |

---

## 二、建议补的（按优先级）

### P0　限流：目前**完全没有**

`grep` 过全部网关代码，没有任何 rate limit / 失败锁定。公网下三个口子最危险：

| 接口 | 风险 | 建议 |
|---|---|---|
| `POST /api/auth/login` | **密码爆破**。无失败计数、无锁定、无验证码 | 按 IP + 用户名双维度：5 次失败锁 15 分钟；整体 IP 每分钟 ≤ 20 次 |
| `POST /api/auth/register` | 邀请码**穷举**。码位够长时风险低，但没有尝试次数限制 | 按 IP 每小时 ≤ 10 次；失败多次直接拉黑一段时间 |
| `POST /api/sessions/:id/jobs` | 已登录用户**刷任务**。单会话串行挡得住一个会话，但**同一用户可以开很多会话并行提交** | 加「单用户同时运行任务数」上限（如 3），超出返回 429 |

> 注意：`running_jobs_count` 这个字段**只是展示用**，并没有拿来做限制。

### P1　SSE 连接数上限

本次修的泄漏是前端 bug，但服务端也应自保：同一用户的 SSE 连接数设上限（如 20），
超出拒绝最旧的。否则任何前端缺陷或恶意脚本都能把连接数打爆
（这次线上就从 14 涨到了 55，没有任何机制拦）。

### P1　prompt 长度后端校验

后端只判了 `!b.prompt`，**没有长度上限**；8000 字符是前端显示，绕过前端就能提交超长 prompt。
每个任务都会进增强（现在还是 agent loop，更贵）。建议后端硬限 ≤ 10000 字符。

### P2　其余

- **`/healthz` 暴露内部细节**（版本、worker 数、并发占用、模型名）。公网建议只回 `{ok:true}`，详情挪到内部接口。
- **错误信息粒度**：登录失败应统一文案，不要区分"用户不存在"和"密码错误"（防用户名枚举）。
- **审计**：`invites.redeem`、admin 操作建议留审计日志，方便事后追溯。
- **出站**：增强 agent 现在能 `WebSearch`/`WebFetch`。它读的是用户 prompt，理论上存在
  **提示词注入 → 让它去抓内网地址**的风险。建议给这个 agent 的出站加白名单，或至少禁掉内网网段。

---

## 三、判断

**按现在的状态放公网，最可能发生的不是"被人白嫖算力"**（邀请码挡住了），
**而是登录接口被爆破**，以及**拿到一个账号后不受限地刷任务**。

补上 P0 的三条限流 + P1 的单用户任务数上限，风险就落到可接受范围。
这些都是网关层的小改动，不碰业务逻辑。

## 三、但 `sleep` 只是表象，真正的浪费是「重渲」

`sleep` 本身不冤 —— 它在等后台的 Puppeteer 抓帧。真实渲染速度是
**每帧 ~1.6 秒**（1830 帧 ≈ 49 分钟的纯渲染量），这部分无法省。

问题在**并行度被反复打断**。08:19 分 4 路并行启动（c0~c3，每路约 456 帧）：

| chunk | 完成耗时 |
|---|---|
| c1 | 11.9 分钟 |
| c2 | 12.1 分钟 |
| c0 | 32.1 分钟 |
| c3 | **65.3 分钟** |

四路帧数几乎相同（456/458），**不是任务不均**。差异来自 agent 中途**删掉重渲**：

```
08:19:03  删除全部 并重渲        ← 首次启动
08:40:01  删除 c0,c3 并重渲      ← 发现缺陷
08:56:50  删除 c3 并重渲          ← 又发现缺陷
09:12:17  删除 c3 并重渲          ← 再一次
```

c3 被渲了 **4 次**。拖尾浪费约 **53 分钟**。

### 重渲是「有理由的」，不是空转

两次重渲前 agent 都明确说明了原因：

- 08:55 `Found a real defect: the world-layer envelope fades the lo…`
- 09:11 `Another real bug: the pen path's segment count was halved,…`

也就是说：**它在自检中发现了真实画面缺陷并修掉**。这是质量换时间，不是 loop 空转。

## 四、如果要压时间，按收益排序

1. **分片后不要整片重渲（最大收益，约 50 分钟）**
   现在发现某一段有问题就 `rm c3.mp4` 整段重来（456 帧 ≈ 12 分钟）。
   可改为只重渲受影响的帧区间，或把 chunk 切得更细（如 8~16 片），
   这样一次返工的代价从 12 分钟降到 2~3 分钟。

2. **先用低分辨率/低帧率过一遍自检再出全量（收益大）**
   两个缺陷都是"画面逻辑"问题（包络淡出、路径段数），
   用 480p / 10fps 抽检就能发现，成本是全量的 1/20。
   现在是直接 1920×1080@30 全量渲完才自检。

3. **`sleep` 改为事件驱动（收益中等）**
   现在是 `sleep 480` 这类固定等待，最长单次 580 秒。
   渲染提前结束也要干等到点。改成轮询退出条件
   （如每 15 秒检查 pid 是否存活）可省掉这部分空等。
   注意：这不减少渲染时间，只减少"渲完了还在等"。

4. **并行度不要再提高（原先判断错了，已更正）**
   后端容器实际配额是 **16 核 / 64 GB**（`cgroup cpu.max = 1600000/100000`）。
   `nproc` 报的 128 是**宿主**核数，容器拿不到 —— 我一开始用了这个数，
   错判成"算力富余"。
   实测负载 **17.4**，已经**略高于 16 核满载**。
   也就是说 4 路 Puppeteer 抓帧已经把 CPU 跑满了，
   **再加并行只会让每帧更慢，总时间不变甚至变差**。
   每帧 1.6 秒在这个配额下是合理水位，不是可优化项。

   > 推论：要缩短纯渲染时间只有两条路 —— 降分辨率/帧率，或者加机器配额。
   > 软件层能省的只有「返工」和「空等」（第 1~3 条）。

## 五、关于机器配额（一处自我更正）

我最初用 `nproc` 读到 128 核，据此判断"算力富余、可以加并行"，**这是错的**。
容器实际配额：

```
/sys/fs/cgroup/cpu.max      1600000 100000   → 16 核
/sys/fs/cgroup/memory.max   64 GB
负载                         17.39 17.44 17.47
```

**16 核、负载 17.4 ⇒ 已经满载。** 查容器配额要看 cgroup，`nproc` 在容器里会报宿主核数。
这改变了结论：并行度不是优化空间，第 1~3 条（减返工、减空等）才是。

### 顺带发现一个容量风险（建议后续评估，本次未改）

渲染期（08:19–09:24）同机只有**这一个任务**在跑
（另一个任务 09:23 才进来、4 分钟就结束），
也就是说：**单个任务自己起 4 路抓帧，就把 16 核跑满了。**

而配置是 `per_machine_max_concurrent_jobs = 4`（dev 与线上一致）。
如果 4 个这种重任务同时落在一台机器上，
每个又各起 4 路渲染 ⇒ **16 路 Puppeteer 抢 16 核**，
每帧耗时会成倍恶化，表现为"大家都变慢"而不是"排队等待"。

两个方向（需要你判断，涉及吞吐与体验的权衡）：
- 降 `per_machine_max_concurrent_jobs`（如 2），牺牲吞吐换单任务速度；
- 或在 skill 里约束 agent 的并行渲染路数（如按 `nproc` 的一半、且上限 4），
  让单任务不要独吞整机。注意：**不能用 `nproc`**，容器里它报 128；
  要读 `/sys/fs/cgroup/cpu.max`。

目前没有实测数据说明 4 个重任务同机会坏到什么程度 —— 要定这个数，
得先压一轮（之前你让我取消的压测正好能回答这个问题）。

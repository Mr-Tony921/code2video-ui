## 固定图片策略与输入保真

白模新增固定策略 `whitebox-media-v2`：长边不超过 1024，保持比例、不裁切；每张优先 64 KiB、硬上限 96 KiB。较大图片依次尝试 JPEG 82/76/70/64，仍超限才继续等比缩小。尺寸及字节合格的小图保留原编码。EXIF 方向归一，JPEG 透明区域合成白底。原图从不覆盖；每次实际模型媒体均保存原始/发送 SHA、尺寸、字节、编码与策略版本。引擎 960 像素宽审查拼图保留分页、布局与标签。

20 张合计约 16.16 MB → 1.41 MB，减少约 91.3%。此数字仅为原始参考图，不包含各次审查拼图、Base64 开销及文本；不会宣称 API 请求固定为 1.41 MB。编码是确定性工具，不产生模型调用，不占反思次数。

业务原始文本中的 `version=2` JSON 直接确定性解析，保留原文、片段字段、固定时长与镜头顺序，避免用模型重新转写完整分镜。普通自然语言仍使用 intake/澄清路径，技术细节继续由 skill 提供。

## 本轮发现的宿主问题

旧上下文保护把“UTF-8 文本字节 + 每图 4096 的保守上界超过预算”当成真实 token 超限。矿坑旧工程的完整 32 页审查证据，估算上界 256230，超过本地输入预留 170667，可能在实际模型请求之前误停。

现在仅用该上界整理可被最新工程替代的重复历史；不据此删掉必要源码、当前要求或当前完整图片证据。真实上下文限制由模型服务执行。服务明确报上下文错误时作为独立控制错误处理，保留当前可回放候选/前次已交付版本，不进入场景修正循环。没有额外压缩模型，也没有消耗 skill 的修正预算。

回归：6 项 Python 媒体/记忆/输入测试通过；真实 Chrome + mock 模型的 runner 回归通过（71.68 秒），包含双任务并发、定向取消、澄清/回答/追问、版本不可变、进程接管及服务确认上下文超限仍保留可回放视频且修正计数为 0。

本批控制层存在一次明确修订：相亲记已经在飞，继续使用旧保护逻辑快照且未触发；林小鱼/矿坑使用修正后的保护逻辑。媒体策略、引擎、模型参数不变。`batch-metadata.json` 保留前后宿主 hash 和原因；本批不能描述为全程冻结代码的严格计时实验。

真实矿坑最终审查已验证该修复：本地上界为 `164114 + 32×4096 = 295186`，明显超过本地输入预留；实际服务返回 `prompt_tokens=67244`，完整正常结束。32 页证据均保留，压缩模型调用和修正预算消耗均为 0。旧逻辑会误拦截这次实际上可接受的请求。

### 矿坑的真实修正路径

首稿错误把 `rotation` 轨道关键帧值写成数字，协议要求 Euler `[x,y,z]`。真实浏览器报泛化 spread TypeError；第一轮模型误修 `entities` 数组，错误仍在；第二轮才把旋转值修正成向量，302 个探针帧、80 镜结构和寻帧通过。两次修正都属于场景源码修正，不是网络重试或上下文压缩，没有超出预算。

独立诊断副本仅转换这四类轨道值，即可通过同一浏览器探针，证明运行失败的直接原因；该副本没有送给模型、没有写回实际任务，也不计入生成成绩。实际第二轮模型自行完成了同一类型修正，保留所有原始记录。

值得给研发反馈的改进点是工具错误定位：在注册轨道时明确报告实体 ID、属性、关键帧时间和期望值类型，比目前泛化的浏览器异常栈更有助于一次修正成功。不应静默猜测旋转轴或替模型改写剧情。此项没有临时改入正在测试的引擎，也没有新增整案重跑来挑选成绩。

### 如何解读质量

相亲记检查全部19个中间帧，主要人物、轮椅、刀具、坐站和近景基本可读；它仍是有限独立检查，不是用户认可或全帧无缺陷保证。

林小鱼检查全部23个中间帧并核对关键源码轨道：掌击后人物没有倒地，庄园缺失应在场的镇国公/文件，茶杯镜头被躯干遮挡。这些是必要结果和取景问题，不是对精细动作的额外要求。

矿坑检查全部80个中间帧，另检查12/56/59/72/74/80镜起中末：12镜下坡抱筐主体缺席，救援与安全落点不可读，后段跪撑承重等镜头被青色矿石严重遮挡。旧包26镜近黑问题在本次未出现，但本次后段遮挡更突出。即使有限合格数量与研发相同，也不能宣称逐案质量对齐。

所有参考图完整进入对应首次生成请求、实际截图进入审查，未发现漏附件或截断时长。当前缺陷直接表现为生成源码的角色状态、空间位置与相机安排问题。没有同条件的原图/压缩图双盲对照，因此不宣称压缩严格无损或对质量完全无影响。

## 耗时究竟在哪里

前两案 API 累计分别占工程时间的 96.9% 和 98.0%，本地工具分别仅18.35秒和19.15秒。这里的 API 包含连接、上传、渠道排队、推理、输出与回传，不是“思考时间”。MP4 渲染完全另计。

- 相亲记六次请求累计连接约3秒、提交144秒、等响应头539秒；返回73653个 reasoning token。
- 林小鱼六次请求累计连接约66秒、提交105秒、等响应头997秒；返回137833个 reasoning token。仅初稿就返回62713个 reasoning token，该请求提交7.3秒、等响应头397秒，因此该次慢不能主要用大图上传解释；仍无法把上游排队与推理完全分开。
- 矿坑最终审查请求3.19MB，257.7秒中有177.5秒花在提交请求（约69%），等响应头79.4秒；实际输入67244 token、推理9097 token。即使每张图已经压缩，完整32页证据在当前网络上依然上传很慢。

结论是模型 API 链路占主要时间，既有显著推理量，也有能直接测到的网络瓶颈；没有证据把所有慢归为推理或 skill 未执行。low 参数确实送出，但不是已验证的服务端思考 token 硬限制。本轮不通过删证据、跳审查、减修正次数来伪造十分钟达标，也不再追加 GPT/Opus 计时试跑。

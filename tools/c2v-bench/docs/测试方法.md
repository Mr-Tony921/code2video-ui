# 测试方法 · c2v-business 0.1.0

## 输入与分组

- 主套件为 19 案目录中的 15 个 ready 案；4 个缺输入案保留但不进入提交/通过率分母。
- `prompt_original` 对应原文；普通案 `prompt_submitted` 只加表格类型；两条通过 gate 的结构案明确增加 Anatomy 视频制作约束。分别记录 `category-prefix-v1` / `category-prefix+anatomy-video-v1`。只上传 `input_assets`，不把成片答案上传给模型。
- 经需求 gate 判断，13 案 `c2v-core-v1`，2 案 `c2v-anatomy-v1`；后者包含固定 Anatomy 包。两组单列，不能掩盖结构任务的额外代价。
- 每个 case × 模型 × skill × 批次建立独立会话、一个首轮任务。harness 内部的自检与工具循环属于该轮；benchmark 不偷偷再发模型修正。
- 模型 revision 或 skill 版本不同分组统计。重跑是新的计划记录，不覆盖历史；人工追问后必须单列，不能计为首轮 pass。
- 当前未配置统一 C2V 时间 SLA；不能直接套白模的 10 分钟或 300 秒视频上限。时长/分辨率以 prompt 或后续明确批准的统一规范为准。

## 网页操作

1. 先检查案例原文、输入图片、参考用途和验收要点。
2. 登录 dev 普通账号，读取实际有权限的模型目录。选择模型、批次，点击“预览并保存测试计划”。此时不调用生成模型。
3. 核对提交配置后，点击提交。测试台走正常会话 → 输入图片上传 → job 排队，不绕过调度、不调用内部接口。
4. 服务端每 30 秒刷新在途任务和会话心跳；前端每 15 秒取本地缓存。不会加载全部轨迹/成片，也不会新建任务作为重试。
5. 任务结束后，同案各模型的视频并排查看。默认 2 倍速粗看，动作、转场、音画同步需 1 倍速核验。
6. 点击“下载原片并完整解码”进行技术检查。网页预览可能经过降采样，不用预览分辨率判原片不合格。大文件及轨迹按需下载。
7. 填写指令遵循、质量结论、瑕疵和对应时间点/证据；保存评审人和时间，修订保留旧评价。导出 JSON（完整记录）或 CSV（统计表）。

## 分层评价

| 层 | 判据 | 当前自动化程度 |
|---|---|---|
| 产物可用 | 网关产物 READY/playable | API 信号，单独显示；不是完整渲染通过 |
| 技术渲染 | 原片 ffprobe 成功、视频流存在，ffmpeg `-xerror` 完整解码成功 | 按需检测，保存 hash、尺寸、帧率、时长和音轨信息 |
| 显式参数 | 20s/60s 等明确时长、16:9 等明确画幅 | 时长容差 max(0.1s,1帧)；画幅比例误差 <0.01；未要求则不判定 |
| 指令硬要求 | 主题、指定品牌/文案、三个 UI、故事/结构、明确素材等 | 人工记录 pass/fail/待审，不能自动由“COMPLETED”推出 |
| 质量 | 风格一致、画面清晰、信息可读、运动/转场、机制可理解、音画同步 | 人工 pass/partial/fail/待审，允许说明局部瑕疵及影响 |
| 知识事实 | 营养、睡眠、物理原理、AirTag 和发明史的准确性 | 人工核验必要事实；漂亮动效不是知识正确性的证明 |

硬要求总通过需要技术检测通过、所有明确参数通过、人工指令检查通过；没有做的部分保留未知。只记录轻微瑕疵不必否定技术可用性，但不能偷偷放宽明确需求。参考片模型未知、非理想效果，且多案内容不对应，不能作为逐像素 gold。

统计同时展示覆盖分母：已提交/已结束、有视频/已结束、解码通过/已检测、硬要求通过/已判定、质量达标/已评价。还要保留已提交总数，避免只选成功视频做分母。0/0 表示尚无证据，不是 0% 或 100%。本轮没有实际生成样本，不报告 pass@1 数字。

## 时间及异常

排队 = `queued_at→started_at`；执行 = `started_at→finished_at`；服务端总时间 = `created_at→finished_at`。客户端会话/附件准备由事件时间补充，不混入纯推理。执行包括模型、工具、检查、视频渲染与平台等待。只有真实轨迹或服务端计时提供分项时，才拆推理/渲染/上传；当前纯推理列固定为空。

同批比较需一致的输入、skill、明确要求、模型配置和平台版本记录。历史 showcase 不作为同条件对照。重试分为 API 传输重试与模型制作循环；HTTP 超时不自动归因于模型能力，记录错误和最后阶段。

创建会话接口目前没有可靠幂等回执保证：请求结果未知时保留 `CREATING_SESSION`，必须在 dev 历史确认空会话 ID 后绑定，不自动创建第二份。图片上传以 SHA note 查询回执，结果不确定且查不到时停下；job 提交复用同一个持久化 Idempotency-Key，避免重复排队。服务重启后需重新登录以恢复心跳/状态查询；不会自动提交未完成计划。

## 验证证据和局限

本轮用独立 API fixture 覆盖正常提交、job 回执丢失后幂等恢复、会话创建回执不确定、输入缺失阻塞、账号隔离、媒体 Range 和统计未知值；另做真实 dev 普通账号的接口与附件适配检查。接口冒烟与原有 Anatomy 两秒视频检查均不能算作这 15 案的质量实验。

可选下一批先选 Mindflow（带图）、微波炉、放映机、NEIGHBOR、咖啡豆、动物视觉验证各主要路径，再完整展开剩余案例。这是测试顺序建议，不代表本轮已排队。

补充：`Violet Flat`、`Pixel Night` 等名称在原文没有完整视觉参数定义，风格对齐先作软评价，不凭未告知模型的参考细节判硬失败。将来若要把风格板/参考截图作为输入，应明确制作变体并统一给所有模型，不能悄悄加入某一组。技能快照证明挂载配置；是否实际调用 core/Anatomy 要看完整轨迹的 Skill 调用，不能仅凭配置字段宣称模型遵循了全部流程。

品牌/指定文案以 prompt 为准。若生成片品牌名错误，记指令偏差；业务参考片来源及其原始 prompt 不明，不预先把参考片认定成某模型的失败。蛋白质/睡眠的单元格对应问题已校正，不列为内容质量缺陷。
